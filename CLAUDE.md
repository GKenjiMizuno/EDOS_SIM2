# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Python simulator (in Portuguese comments/logs, TCC/thesis project) that models autoscaling behavior under normal load and EDoS-style (Economic Denial of Sustainability) HTTP flood attacks. It spins up a target web app as Docker containers, drives traffic against them, autoscales based on CPU, and logs metrics/RTT/packet captures for later analysis (entropy, plots).

There is no test suite, linter, or build step in this repo — it's an experimental/research harness, run directly with Python. Docker must be installed and running. The simulation needs privileges to run `tcpdump`; historically this meant invoking everything with `sudo`, but current environments grant the `tcpdump` binary `cap_net_raw,cap_net_admin` directly (`sudo setcap cap_net_raw,cap_net_admin=eip $(which tcpdump)`, a one-time host-level setup step, not a repo file), so `sudo` is no longer required day-to-day — `run_experiments.py`, `run_experiments_normal.py`, and `run_experiments_combined.py` all had their hardcoded `"sudo"` subprocess argument removed for this reason (see `changes.txt` §34). If packet capture stops working after a `tcpdump` package update (which replaces the binary and resets the capability), re-run the `setcap` command.

## Running the simulator

```bash
pip install -r requirements.txt   # docker, requests (pandas/numpy/matplotlib/openpyxl also needed for analysis/plot scripts, not pinned)

# single run
python main_orchestrator.py [--rps FLOAT] [--attackers INT] [--duration INT] [--work-units INT] \
    [--attack-duration INT] [--normal-rps FLOAT] [--normal-work-units INT] [--attack-start INT] [--pulse-duration INT]

# sweeps (each writes into its own experiment_results/ subfolder; no sudo needed, see setcap note above)
python run_experiments_normal.py    # normal-traffic-only baselines -> experiment_results/normal_baseline/
python run_experiments.py           # attack-only WU/RPS calibration -> experiment_results/wu_calibration/
python run_experiments_combined.py  # normal + attack overlay (Table 5-style) -> experiment_results/combined_sweep/

# post-processing (pure CSV/XLSX processing)
python run_burst_analysis.py            # runs EntCusumZV3's burst detector over every rtt_log_*.csv found recursively under experiment_results/
python generate_presentation_graphs.py  # reads experiment_results/combined_sweep/ -> graficos_apresentacao/*.png (heatmap, bar summary, per-run detection panel)
```

A separate, newer `wedos_*.py` suite (not the three sweep scripts above) drives a more rigorous W-EDoS characterization with repetitions — see "W-EDoS characterization suite" below.

There's no automated test runner; the self-test blocks under `if __name__ == "__main__":` in `docker_manager.py`, `autoscaler_logic.py`, `normal_traffic.py`, and `traffic_injectorV0.py` are the closest thing to tests — run a module directly (e.g. `python docker_manager.py`) to exercise it standalone. These self-tests actually build the Docker image and start/stop real containers, so Docker must be running.

All tunables (simulation duration, CPU thresholds, attack timing, work-unit intensity, ports, network name, log file names) live in `config.py` — check there first before changing behavior in other modules.

## Architecture

`main_orchestrator.py` is the single entry point and owns the whole simulation loop; every other module is a passive service it calls into on a fixed tick (`config.MONITOR_INTERVAL_SECONDS`, drift-corrected via `time.monotonic()` + `next_tick`). Per iteration it:

1. Refreshes container stats via `StatsCollector` (background-polling thread, `stats_collector.py`) — CPU% and app memory (usage minus page cache) per container, averaged across active instances.
2. Asks `autoscaler_logic.Autoscaler.decide_scaling(avg_cpu, num_instances)` for `SCALE_UP` / `SCALE_DOWN` / `NO_ACTION`, applies it via `docker_manager.start_instance()` / `stop_instance()`, and updates the autoscaler's cooldown state (`record_scale_action`).
3. Re-derives each active container's published host port (via `container.reload()` + `NetworkSettings`) to build target URLs, then drives traffic:
   - Normal traffic (`normal_traffic.start_http_traffic` / `stop_http_traffic`) — steady background load with Poisson-distributed inter-arrival times per client (models independent clients, per Sotelo Monge et al.), round-robin across instances, tags requests with `?work=<NORMAL_WORK_UNITS>&sleep=<NORMAL_SLEEP>`. Runs for the entire simulation and is only stopped explicitly at the very end.
   - Attack traffic (`traffic_injectorV0.start_http_flood` / `stop_http_flood`) — a **single, non-repeating window**: starts once at `ATTACK_START_TIME_SECONDS`, runs for `PULSE_DURATION` seconds, stops once, never re-schedules (the earlier Yo-Yo-style repeating-pulse design was retired — `SCALE_COOLDOWN_SECONDS` has no role in attack scheduling anymore, only in the autoscaler's own cooldown between scaling actions). Tags requests with `?work=<ATTACK_WORK_UNITS>&sleep=<ATTACK_SLEEP>`. The injector is restarted (stopped and relaunched with fresh target URLs) whenever the instance count changes while the attack is active, so load stays spread across the current fleet — note normal traffic does **not** get this same restart-on-scale treatment; its target URL list is fixed at start time. Also note there is a `traffic_injector.py` with an equivalent-but-different (`duration_seconds`-based) attack API that is **not** imported anywhere — the orchestrator only imports `traffic_injectorV0`; don't confuse the two.
   - Both injectors are open-loop (a `ThreadPoolExecutor`-backed send pool decoupled from the per-worker pacing loop, so a slow target doesn't throttle the achieved send rate) and record round-trip times into module-level lists; `get_average_rtt_ms()` / `get_average_rtt_attack_ms()` drain those lists each time they're called (call-and-reset semantics, not a running average). `get_average_rtt_ms()` (normal-traffic RTT) is called **every** iteration regardless of phase specifically to keep draining it during the attack window — normal traffic never stops, so skipping the drain during attack-labeled iterations would let samples silently pile up and distort the first post-attack row's average.
4. Logs one row per iteration to `config.METRICS_LOG_FILE` (elapsed time, instance count, avg CPU/mem/RTT, decision, active container names, `label` normal/attack) and appends to `instance_intervals_for_cost` for the end-of-run fictional cost total (`cost_calculator.py`). During attack-labeled iterations, `avg_rtt_ms` is attack-only RTT (from `get_average_rtt_attack_ms()`), not blended with concurrent normal traffic — keep this in mind when comparing this column against `rtt_log.csv`, which mixes both.
5. A `TcpdumpSniffer` (`tcpdump_sniffer.py`) runs for the whole simulation as a separate `tcpdump` subprocess (`-i any`, filtered to a BPF `portrange` covering the target instances' published host ports — not by network interface, since the client-side traffic against `http://localhost:<port>` rides the loopback interface, not the Docker bridge), parsing live packet lines into `config.TCPDUMP_OUTPUT_CSV` and stamping each row with whatever label (`benign`/`attack`) the orchestrator has set via `sniffer.set_label()` at that point in the loop — this is the ground-truth label for downstream traffic-classification work.

The target application under test is `app/simple_server.py`, a stdlib `ThreadingHTTPServer` (HTTP/1.1 keep-alive enabled — required to avoid ephemeral-port/TIME_WAIT exhaustion under sustained load) whose per-request CPU cost and latency are controlled purely by query params (`?work=N&sleep=S`, defaulting to env vars `WORK_UNITS`/`PROCESSING_TIME`) — `work` submits a `math.sqrt`/`math.sin` loop of N iterations to a **persistent `ProcessPoolExecutor`** (`INSTANCE_MAX_CONCURRENT_REQUESTS` workers, created once at server startup, not per-request) for real cross-core parallelism, and blocks on `.result()`; `sleep` adds fixed latency on top. It's built into the `edos_target_app` image via the root `dockerfile` and run as `target_instance_N` containers on a dedicated bridge network (`config.DOCKER_NETWORK_NAME`), one published host port per instance starting at `STARTING_HOST_PORT`.

`docker_manager.py` wraps the Docker SDK for image build, network setup, container lifecycle, and cleanup (`cleanup_all_simulation_instances`, filtered by `BASE_CONTAINER_NAME` prefix — safe to call repeatedly, won't touch unrelated containers). It exposes both an SDK-stats CPU reader (`get_container_stats`, single snapshot) and a `docker stats --no-stream` CLI-based fallback (`get_container_cpu_percent`); the orchestrator's live metrics actually come from `StatsCollector`'s own polling loop in `stats_collector.py`, which duplicates the CPU% formula independently.

`analyze_traffic.py` and `plot_graphs.py` are older standalone offline analysis scripts (not imported by the orchestrator) — RTT entropy per time window and CPU/instance/memory time-series plots respectively. Largely superseded by `EntCusumZV3.py` (entropy + Z-score + CUSUM together) and `generate_presentation_graphs.py`; still present but not part of the current workflow. Hardcoded filenames at the top of each (`INPUT_FILE`, `CSV_FILE`) need to be edited by hand to point at a specific run's output before use.

`main_orchestrator_back.py` is a backup/older version of the orchestrator kept alongside the current one — don't confuse the two; the current entry point is `main_orchestrator.py`.

Three sweep scripts drive `main_orchestrator.py` via its CLI overrides (`--rps`, `--attackers`, `--work-units`, `--attack-duration`, `--normal-rps`, `--normal-work-units`, `--attack-start`, `--pulse-duration`) and each writes into its **own subfolder** of `experiment_results/` (`RESULTS_DIR` constant at the top of each script): `run_experiments.py` → `wu_calibration/` (attack-only, sweeps RPS × attackers × work units), `run_experiments_normal.py` → `normal_baseline/` (normal-traffic-only baselines, `--attack-duration 0`), and `run_experiments_combined.py` → `combined_sweep/` (normal + attack overlay together, attack volume expressed as a percentage of the normal scenario's aggregate request rate — see that script's `NORMAL_SCENARIOS` dict, which is calibrated against this simulator's own measured capacity curve, not copied from the reference paper's Table 4 numbers, since the paper's testbed has a different capacity). All three scripts move `simulation_metrics.csv`, `attack_summary_log.csv`, `rtt_log.csv`, **and** `traffic_capture.csv` into their `RESULTS_DIR` with scenario-specific filenames after each run — none of these four files are safe to read from the repo root after a sweep, they're all overwritten by whatever ran last. (`run_experiments_normal.py` discards `attack_summary_log.csv` instead of saving it, since it's just an empty header with no attack running.)

### W-EDoS characterization suite (`wedos_*.py`)

A newer, more rigorous characterization suite than the three original sweep scripts, built in a 12/08→13/08 session and run end-to-end (results committed). It runs a 5-phase plan (see `PLANO_WEDOS_STATUS.txt` for the fine-grained checklist and `RELATORIO_WEDOS_13_08.txt` for the full write-up — both kept in the repo root as the durable record; re-read them before re-running or extending this suite instead of re-deriving the plan from scratch):

- **Phase 0** (calibration/validation, read-only or corrective): `wedos_structural_audit.py` (read-only integrity check over all of `experiment_results/`), `wedos_repro_test.py` (repeats known boundary points in two batches to test for session-length environment drift), `wedos_s3_mystery.py` (reran the `S3_atk1pct_wu300000` anomaly from `changes.txt` §31 three times — did **not** reproduce the original ~490-error spike, most reruns showed 0-32 errors, so it looks like a one-off rather than a systematic bug, but this isn't a confirmed root cause), and a fine threshold sweep that confirmed the normal-baseline capacity ceiling sits at **~205-210 aggregate req/s (WU=10)** — this is why S4 (300 aggregate, from the original `NORMAL_SCENARIOS`) was excluded from the finer sweeps below: it's already unstable with zero attack traffic.
- **Phase 1** (`wedos_combined_grid.py stage1a`/`stage1b`, writes to `experiment_results/wedos_grid/`): combined normal+attack sweep like `run_experiments_combined.py` but with a wider grid (Stage1A, 48 points, 1 rep) followed by fine-grained refinement with real repetitions around the boundaries found (Stage1B, 31 runs across S1-S3; `wedos_stage1b_refined.py` is the canonical script, `wedos_stage1b_resume.py` a one-off resumption after a mid-run interruption — safe to delete once superseded).
- **Phase 2** (`wedos_ent_cusum_report.py`, reads the `.xlsx` files `run_burst_analysis.py` already produced, writes `experiment_results/wedos_ent_cusum_*.csv`): consolidates entropy/Z-score/CUSUM burst-detection stats for specific candidate globs of `rtt_log_*.csv`.
- **Phase 3** (`wedos_graphs.py`, writes `graficos_apresentacao/06`-`09`): final presentation graphs reading Phase 1/2/4 output.
- **Phase 4** (`wedos_failure_sweep.py wu|rps|attackers|all`, writes to `experiment_results/wedos_failure/`): isolated (no normal traffic) OFAT sweep along WU/RPS-per-attacker/attacker-count, starting from the already-known worst case (`rps=10, WU=500000, 4 attackers`) to see how much worse a already-collapsed attack gets — it does **not** resolve the fine failure boundary itself (that boundary, between WU=100000 and WU=200000 at this RPS, was already mapped by `run_experiments.py`/`wu_calibration`; Phase 4's WU axis starts at 400000, already past it).

**Key finding** (the thesis-relevant result of this whole suite — see `RELATORIO_WEDOS_13_08.txt` §1 for full detail): a W-EDoS attack overlaid on normal traffic can force real `SCALE_UP` decisions while remaining **completely undetected** by `EntCusumZV3.py`'s RTT-based burst detector — confirmed reproducibly (S2 scenario, 1% attack intensity, WU=500000: `SCALE_UP` in 3/3 repetitions, 0 burst-flagged windows out of 56 total; S3 scenario, 1% intensity, WU as low as 100000: 0/15 independent runs flagged). A control run of the *same* attack level in isolation (Phase 4, no normal traffic diluting the RTT signal) raises detection to 80-87.5% of windows — confirming this is the dilution effect already documented as caveat (1) on `EntCusumZV3.py` below, not a detector bug.

`EntCusumZV3.py` is a standalone, offline statistical-analysis module (Phase 3.5 tooling, not imported by the orchestrator) whose `analisar_bursts_tunavel(input_file=..., output_prefix=None, ..., baseline_ratio=1.8, show_plot=True)` runs a sliding-window burst detector over an `rtt_log_*.csv`: for each window (`window_seconds=20` default, `overlap_percent=50` → 10s stride) it computes Shannon entropy of the RTT distribution, a Z-score against the *previous* window's mean/std, and a classic one-sided CUSUM statistic. Both the CUSUM reference (`global_mean`/`global_std`) and the burst floor are computed from that **specific run's own pre-attack baseline** (samples before `config.ATTACK_START_TIME_SECONDS`, falls back to whole-file stats if fewer than 10 such samples exist) — not a fixed constant and not the whole file — because RTT baselines vary enough across RPS/WU scenarios (measured 15-64ms) that neither a fixed threshold nor a whole-file (attack-contaminated) CUSUM reference works across scenarios. The burst floor is `baseline_mean * baseline_ratio` (a ratio, not `mean + k*std`, because there's usually only ~20s/one window's worth of clean pre-attack data — not enough to estimate a window-level standard deviation reliably). A window is flagged `'DDoS Burst'` when its mean RTT exceeds that floor and either the Z-score or CUSUM alarm fires. Called with no arguments it preserves the original default output filenames (`rtt_bursts_tunaveis.xlsx`, `rtt_todos_bursts.png`) for manual/interactive use; called with an `input_file` (as `run_burst_analysis.py` does, batch-processing every `rtt_log_*.csv` found recursively under `experiment_results/`) it derives matching output filenames and writes them alongside the input. Known caveats: (1) it has no awareness of which samples in `rtt_log.csv` are attack vs. normal (that file mixes both without a per-row label) — at low attack intensity relative to normal volume, the attack's RTT signal gets diluted into the window mean and can go undetected even though it's real and measurable via `simulation_metrics.csv`'s attack-only RTT column; this is expected given W-EDoS's stealth premise, not a bug (see `changes.txt` §27). (2) it also loses *coverage*, not just sensitivity, when the target fails outright: failed/timed-out requests never produce an RTT sample, so severe attacks with real request failures can end up with fewer analyzable 20s windows than milder ones, undercounting exactly the worst periods (see `changes.txt` §27's `S4_atk10pct_wu500000` example). (3) no awareness of the `label` column in `simulation_metrics.csv` or `traffic_capture.csv`, so it can't self-report TPR/FPR against ground truth — that comparison has to be done by eye.

## Known inconsistencies to be aware of

- `traffic_injector.py` vs `traffic_injectorV0.py` and `main_orchestrator.py` vs `main_orchestrator_back.py` are parallel versions from different iterations — confirm which one is actually imported/run before modifying "the" version of either. Only `traffic_injectorV0.py` and `main_orchestrator.py` are live.
- `docs/*.md` describe an earlier version of the simulation (simpler flat-rate attack, `PROCESSING_TIME` env-var sleep in `simple_server.py`, function-based non-class `autoscaler_logic`, pulsed Yo-Yo-style attack) and no longer match the current code (class-based `Autoscaler`, work-unit-based CPU load, single-window sustained W-EDoS attack, ProcessPoolExecutor + keep-alive in `simple_server.py`, tcpdump sniffing, stats collector thread). Treat them as historical context, not a spec.
- The `overnight_*.py` scripts (from an earlier 11/08→12/08 session, documented in `RESUMO_MADRUGADA_12_08.txt`) were deleted after being functionally superseded by the `wedos_*.py` suite; `wedos_stage1b_refined.py`'s docstring still references `overnight_threshold_sweep.py` by name as the historical source of the ~205-210 capacity-ceiling finding — that's a stale filename in a comment, not a live import, the finding itself still holds.
- `config.py` no longer carries the old pulsed-attack (`EDOS_PULSE_*`/`EDOS_IDLE_*`/`EDOS_SATURATION_*`) or `TCPDUMP_INTERFACE` constants — both were removed (not just unused) when the attack model moved to a single sustained window and the sniffer moved to port-range-based filtering, respectively. If you see either referenced anywhere outside `changes.txt`'s history, that reference is stale.
- `attack_summary_log.csv` rows only come from **attack** workers (`traffic_injectorV0.py` calls `attack_summary_logger.log_worker_stop`); `normal_traffic.py`'s workers never log there, by design — don't expect normal-traffic request/error counts in that file. Normal-traffic request/error counts now **do** get persisted, just to a separate sibling file: `config.NORMAL_TRAFFIC_SUMMARY_LOG_FILE` (`normal_traffic_summary_log.csv`), written by the new `normal_traffic_summary_logger.py` (mirrors `attack_summary_logger.py`'s structure) — before this fix (`changes.txt` §35) that data only ever hit the console and was never analyzed, in every prior run including the original `combined_sweep`/`wu_calibration` datasets.
- `attack_summary_log_S3_atk1pct_wu300000.csv` (in `experiment_results/combined_sweep/`) originally showed ~490 request errors despite a planned attack rate of only ~2 req/s aggregate (`changes.txt` §31). Reran 3× in `wedos_s3_mystery.py` (`experiment_results/wedos_grid/*_mystery_rep{1,2,3}.csv`) — none reproduced the spike (0, 32, and 29 errors respectively) — so it looks like a one-off (transient Docker/host hiccup, not a reproducible bug), but the root cause is still not confirmed.
